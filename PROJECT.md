# TimeGuard — документ передачи проекта

Родительский контроль экранного времени для двух ПК с Windows.
Один ПК — **клиент** (ребёнок), второй — **родитель**. Основной канал управления временем —
подписанные **коды**, которые родитель диктует/передаёт, а ребёнок вводит на заглушке:
**коды работают офлайн**. История приложений, онлайн-команды, запросы времени, обнаружение
и обновления используют **LAN/интернет** (порты и протокол — §14). Этот файл — точка входа для нового разработчика: что где лежит, как собрать,
как это работает и что осталось доделать.

> Короткий пользовательский README — в `README.md`. Здесь — инженерная картина целиком.

## 1. Как собрать и запустить

- Требуется **.NET SDK 8** (на машине стоят 8/9/10; проекты таргетят `net8.0` / `net8.0-windows`).
- Решение в новом формате: **`TimeGuard.slnx`** (dotnet 10 создаёт `.slnx`, не `.sln`).

```
dotnet build TimeGuard.slnx -c Release          # собрать всё
dotnet test tests/TimeGuard.Core.Tests          # прогнать тесты
```

Публикация (самодостаточные exe, на целевых ПК .NET ставить не нужно):

```
# клиент (служба + агент в одну папку installer\publish):
powershell -ExecutionPolicy Bypass -File installer\build.ps1 -OutDir "E:\My projects\TimeGuard\installer\publish"

# родитель:
dotnet publish src\TimeGuard.Parent\TimeGuard.Parent.csproj -c Release -r win-x64 --self-contained true -o publish-parent
```

> ⚠️ У `installer\build.ps1` при запуске с относительным путём `$PSScriptRoot` пуст, и вывод
> уходит в корень диска. **Всегда** передавай `-OutDir` с абсолютным путём (как выше).

Репозиторий — GitHub `kbelousov-ency/TimeGuard`. Релизы собираются по тегу `v*` через
`.github/workflows/release.yml`. Скрипты `.ps1`/`.cmd` сохранены в UTF-8 с BOM — иначе Windows
PowerShell 5.1 ломает кириллицу. При правке сохраняй кодировку.

## 2. Архитектура

Три исполняемых модуля + общая библиотека.

| Проект | TFM | Роль |
|---|---|---|
| `TimeGuard.Core` | net8.0 | коды, протокол канала, движок логики, модель состояния |
| `TimeGuard.Service` | net8.0-windows | Windows-служба (LocalSystem): учёт времени, хранение, запуск агента, политики, лог активности |
| `TimeGuard.Agent` | net8.0-windows (WPF) | UI в сессии ребёнка: индикатор времени и полноэкранная заглушка |
| `TimeGuard.Parent` | net8.0-windows (WPF) | приложение родителя: генерация кодов, экспорт сопряжения |
| `TimeGuard.Core.Tests` | net8.0 (xUnit) | тесты кодека, движка и LAN-протокола (подпись, повтор, лимиты, обнаружение) |

Весь UI написан **кодом** (без XAML-файлов): у Agent и Parent свой `Program.Main` со `[STAThread]`.

### Поток работы (коды, офлайн)
1. Родитель при первой настройке генерирует секрет (32 байта), `machineId` (GUID) и мастер-пароль,
   сохраняет локально и **экспортирует `pairing.json`** (секрет + machineId + хэш мастера).
2. `pairing.json` переносится на клиент и импортируется в службу (`--import`).
3. Служба на клиенте считает время активной сессии ребёнка, при исчерпании — заглушка на весь экран.
4. Родитель генерирует код на N минут → ребёнок вводит на заглушке → служба проверяет подпись
   локально тем же секретом → добавляет время. Мастер-пароль открывает всегда.

Сетевые функции (история, онлайн-команды, запрос времени, обнаружение) работают поверх этого
по LAN и не нужны для кодов; см. §5, §7 и §14.

## 3. Коды (`TimeGuard.Core/TimeGuardCodec.cs`)

Три вида, все проверяются офлайн общим HMAC-секретом и привязаны к `machineId`
(чужой паре код не подойдёт).

- **Временный код** — 9 цифр `XXX-XXX-XXX`. Первые 3 — минуты (0..999), последние 6 —
  подпись `HMAC-SHA256(secret, machineId || минуты || шаг)` mod 10^6. **TOTP-подобный**:
  шаг = unix-время / 60, в код не пишется, клиент перебирает шаги в окне `±WindowSteps`.
  Сейчас `PeriodSeconds=60`, `WindowSteps=10` → код живёт ~10 минут, часы ПК терпят расхождение до ±10 мин.
  Счётчика нет → **любой** родительский ПК с тем же секретом генерирует валидные коды независимо.
  Защита от повтора — оконная: движок хранит принятые теги до истечения окна (`GuardState.ConsumedCodes`).
- **Резервный код** — 10 цифр `XXX-XXX-XXXX`. Индекс(1)+минуты(3)+подпись(6), **без времени**,
  одноразовый, детерминированный (набор из 10 кодов на заданные минуты всегда одинаков; на любом
  родительском ПК совпадает). Погашенные хранятся навсегда в `GuardState.UsedBackupCodes`.
  Ночью не действуют. Клиент отличает по длине: 9 цифр → временный, 10 → резервный.
- **Мастер-пароль** — PBKDF2-SHA256, 200000 итераций (`MasterPassword.cs`). Открывает всегда,
  в т.ч. снимает ночной запрет.

Ввод кода на заглушке **не зависит от раскладки**: принимаются только цифры по физическим
клавишам, дефисы проставляются автоматически (`OverlayWindow.CodeBox_PreviewKeyDown`).

## 4. Движок (`TimeGuard.Core/GuardEngine.cs`)

Потокобезопасный (один замок). Держит `GuardState`, `GuardConfig`, кодек, часы (инъектируются в тестах).

Правила блокировки:
- **День**: заблокировано, когда `RemainingSeconds <= 0`.
- **Ночь (комендантский час)**: заблокировано всегда, время **не списывается**, снять можно
  **только мастер-паролем** (он ставит флаг `CurfewOverridden` до конца ночи; коды и резервные коды ночью отклоняются).
  Часы ночи — в конфиге (`CurfewEnabled`, `CurfewStartHour=21`, `CurfewEndHour=9`).

`Tick(elapsed, sessionActive)` списывает реально прошедшие секунды по монотонному счётчику
(`Stopwatch`, устойчиво к переводу системных часов), только когда сессия ребёнка активна, не ночь и остаток > 0.

`ResetToZero()` — мгновенная блокировка (см. reset.flag ниже): обнуляет остаток и снимает `CurfewOverridden`.
Коды отклоняются весь ночной период, в том числе после мастер-пароля. Днём мастер-пароль добавляет 120 минут.

Важно про счётчик времени: он идёт, **пока ребёнок в системе за консолью и экран разблокирован**,
независимо от того, запущено ли какое-либо приложение и есть ли активность.
Состояние блокировки Windows проверяется через `WTSQuerySessionInformationW(WTSSessionInfoEx)`;
при неизвестном состоянии время не списывается. Watchdog продолжает работать и при блокировке Windows.

## 5. Служба (`TimeGuard.Service`)

`Worker.cs` — главный цикл (тик 1 с):
- Загружает `GuardConfig`; если нет — ждёт установки пары.
- Считает время (`GuardEngine.Tick`), пушит статус агенту по каналу.
- Определяет активную консольную сессию и **целевого пользователя** (`GuardConfig.TargetUser`):
  ограничение применяется **только** к учётке ребёнка; под админом блокировки и списания нет
  (`IsTargetSessionActive`). Если TargetUser пуст — ограничивает любого (обратная совместимость).
- Запускает агент в сессию ребёнка (`SessionLauncher`), watchdog перезапускает убитый агент.
- Применяет политику блокировки Диспетчера задач в кусте HKU целевого пользователя (`PolicyGuard`).
- Ловит **reset.flag** (мгновенный сброс), определяет **сон** (по разрыву стенных часов),
  пишет **лог активности** (`ActivityLog`).
  Опрос приложений выполняется только при активной целевой учётке (при пустом `TargetUser` — для любой).
- Пока реально списывается время, сохраняет запуск и закрытие приложений целевой сессии.
- Поднимает LAN HTTP endpoint истории на TCP `38765`; запросы родителя проверяются HMAC-секретом пары.
- Обслуживает подписанные команды родителя на этом же endpoint, включая статус, добавление минут и сброс.
- Отвечает на UDP-маяки родителя на порту `38767` (`ParentDiscoveryListener`), запоминает адрес родителя.
- **Сеть не должна ломать учёт.** `HistoryServer` и `ParentDiscoveryListener` создаются и запускаются через
  `NetworkComponents` в `Worker.cs`: любое исключение создания/запуска только пишется в лог (Warning),
  главный цикл учёта стартует даже если оба компонента не поднялись. Причина: SocketException в
  `ExecuteAsync` при `BackgroundServiceExceptionBehavior.StopHost` (.NET 8) останавливал хост, служба уходила
  в цикл перезапусков и лимиты не действовали; порт выше 1024 может занять стандартный пользователь.
  UDP-сокет: `ExclusiveAddressUse = true`, бинд внутри `RunAsync` с повтором раз в 30 с и одним Warning в лог.
  `HistoryServer` при занятом TCP `38765` пишет Warning и не повторяет бинд до перезапуска службы.
- Запрос дополнительного времени от клиента: `RequestParentTimeAsync` шлёт подписанный POST
  `/timeguard/request-time` родителю (порт `38766`), см. §14.3. **Минуты по ответу родителя служба не
  добавляет**: ответ не подписан, а адрес родителя может подменить ребёнок. Время добавляется только когда
  родитель сам присылает подписанную команду `add` на `/timeguard/control` этой же службы.

`Program.cs` — служебные команды (запускаются от админа):
- `--import <pairing.json>` — импорт сопряжения в конфиг.
- `--set-user <имя>` — задать учётку ребёнка (target user).
- `--set-curfew <start> <end> [on|off]` — настроить ночной запрет.

`Ipc/PipeServer.cs` — именованный канал `\\.\pipe\TimeGuard`, ACL: SYSTEM/Admins — полный,
Interactive — чтение/запись. Служба (session 0) шлёт статус агенту (session ребёнка), принимает коды/мастер.

`Interop/`:
- `NativeMethods.cs` — P/Invoke. **STARTUPINFO помечена `CharSet.Unicode`** — это критично (см. §9).
- `SessionLauncher.cs` — WTSGetActiveConsoleSessionId / WTSQueryUserToken / DuplicateTokenEx /
  CreateProcessAsUser. **Командная строка обязательна** (argv[0]), иначе .NET-хост не стартует (см. §9).
- `PolicyGuard.cs` — DisableTaskMgr в HKU\<SID> ребёнка.

`Storage/StateStore.cs` — конфиг и состояние в `%ProgramData%\TimeGuard`, шифрование **DPAPI
(LocalMachine)**, атомарная запись через .tmp + Move.

## 6. Агент (`TimeGuard.Agent`, WPF)

- `IndicatorWindow.cs` — нажатие на таймер открывает `ExtendTimeWindow.cs` (заменило кнопку «+ Время»).
  Днём до блокировки можно ввести обычный или резервный код: минуты прибавляются к остатку,
  таймер во время ввода продолжает идти. Ответ службы отображается в окне; повторный код отклоняется.
  Окно немодальное, закрывается при блокировке, ночном режиме или потере связи со службой.
  Ночью нажатие на таймер не открывает ввод кода даже после мастер-разблокировки.

- `PipeClient.cs` — клиент канала, автопереподключение. **Пишет в поток без Flush** (см. §9).
- `AgentApp.cs` — оркестратор: индикатор + заглушка по статусу, признак ночи.
- `OverlayWindow.cs` — полноэкранная заглушка на всех мониторах, topmost, без сворачивания/закрытия,
  возврат на передний план каждые 700 мс, поля ввода кода (цифры, любая раскладка) и мастер-пароля,
  ночной/дневной заголовок. Позиционируется по пиксельным границам монитора (`MoveWindow`).
  Внутри поля мастер-пароля — индикатор раскладки «⌨ RU»/«EN» (`LayoutSwitch`): пароль зависит от языка ввода.
  Клик переключает на следующий язык из `InputLanguageManager.AvailableInputLanguages`; при одной раскладке кнопка
  неактивна. Надпись обновляется по `InputLanguageChanged` и по таймеру 700 мс (Alt+Shift хук не глушит, Win+Space глушит).
  Кнопка `Focusable=false`, фокус остаётся в поле пароля.
- `KeyboardHook.cs` — low-level hook: глушит Win / Alt+Tab / Alt+Esc / Ctrl+Esc / Alt+F4.
  **Ctrl+Alt+Del перехватить нельзя** (ограничение Windows), но сам он заглушку не снимает.
- `Program.cs` — single-instance mutex, лог агента в `C:\Users\Public\TimeGuard-agent.log` (диагностический, см. §10).

## 7. Родитель (`TimeGuard.Parent`, WPF)

- `MainWindow.cs` — окно по фирменному концепту (шапка с логотипом, карточка клиента,
  «Управление временем» с пресетами и полем лимита, «Код управления», «Настройка клиента», подвал).
  Кнопка «История приложений» открывает `HistoryWindow` и запрашивает журнал клиента по имени или IP.
  «Онлайн-управление» запускает сервер запросов на TCP `38766`, показывает запросы времени и даёт approve/reject.
  При одобрении родитель сам отправляет подписанную `add` на `/timeguard/control` клиента (`ParentOnlineServer.ResolveAsync`
  → `AddOnClientAsync`); клиенту уходит `Accepted=true`, только если клиент подтвердил добавление (§14.3).
  Автообнаружение (`ParentOnlineServer`): два независимых цикла — маяк раз в 5 с и постоянный приём ответов
  (раньше новый `ReceiveAsync` каждые 5 с оставлял старый висеть, и тот съедал пакет). Если UDP `38767` занять не удалось
  (второй экземпляр родителя, клиент на этом же ПК), `Start()` не бросает исключение: окно открывается,
  `DiscoveryError` заполнен, а `MainWindow` показывает подсказку «автообнаружение недоступно» (адрес вводится вручную).
  Иллюстрации нарисованы **векторно**; если положить `assets\logo.png` / `avatar.png` / `monitor.png`
  рядом с exe — подставятся они (см. csproj: копирование `..\..\assets\*.png`).
  Макет рисуется в ширине 1040 DIP и компактно уменьшается до ширины около 610 DIP. Чёткость текста поддерживается настройками WPF-рендеринга.
  Офлайн-адаптация: «+N мин» и «Установить» **генерируют код**, а не меняют лимит напрямую.
- `SetupWindow.cs` — первичная настройка: «Создать пару» или **«Импортировать файл сопряжения…»**
  (для установки родителя на второй ПК с тем же секретом).
- `ParentStore.cs` — конфиг родителя в `%APPDATA%\TimeGuardParent\parent.dat`, DPAPI (CurrentUser).
- `Pairing.cs` — экспорт/импорт `pairing.json` (это тот же файл, что идёт на клиент).

## 8. Установка и эксплуатация (скрипты в `installer\`)

### Универсальные EXE-установщики

Готовые `TimeGuard-Parent-Setup.exe` и `TimeGuard-Client-Setup.exe` публикуются в [GitHub Releases](https://github.com/kbelousov-ency/TimeGuard/releases) и включают .NET и все файлы. При локальной сборке они появляются в `installer/dist`.
Родитель устанавливается в `%LOCALAPPDATA%\Programs\TimeGuardParent`, клиент — в Program Files с UAC.
Сначала на родительском ПК создайте пару и экспортируйте JSON через «Экспортировать файл сопряжения…».
Перенесите JSON с клиентским EXE, выберите файл в установщике. Текущая интерактивная учётная запись
определяется автоматически и должна быть стандартной. Новые учётные записи установщик не создаёт.
JSON содержит секрет пары.
Изначально EXE использовали строку Base64 через «Показать строку сопряжения»; этот вариант отклонён
пользователем как неудобный для переноса между ПК. Кнопка удалена, снова используется файл.
Установщики универсальные, существующий `pairing.tgpair.json` в них не включается.
При обновлении клиента поле файла можно оставить пустым: сохраняется существующая конфигурация.
Удаление доступно через установленные приложения Windows; данные пары и остаток сохраняются.

Сборка: `powershell -NoProfile -ExecutionPolicy Bypass -File installer\build-installers.ps1`.
Нужен Inno Setup (`-Compiler <путь к ISCC.exe>`; локально `installer/tools/Inno/ISCC.exe`).
Исходники: `parent.iss`, `client.iss`, `configure-client.ps1`; промежуточные публикации в `installer/stage`.
EXE скомпилированы; установку/удаление службы на настоящем ПК ребёнка требуется проверить отдельно.

Все `.cmd` самоподнимаются до администратора (UAC).

| Файл | Что делает |
|---|---|
| `build.ps1` | публикует службу+агент в `publish` |
| `Install-Client.cmd` → `install.ps1` | копирует файлы в `Program Files\TimeGuard`, импортирует `pairing.json`, автоматически задаёт target-user текущей интерактивной учёткой, регистрирует службу и запускает её |
| `Update-Service.cmd` → `Update-Service.ps1` | останавливает службу, ждёт завершения, обновляет файлы, показывает их даты, стартует |
| `Uninstall-Client.cmd` → `uninstall.ps1` | снимает политики, удаляет службу и файлы (`-PurgeData` — ещё и состояние) |
| `Set-Child.cmd` | привязать ограничение к учётке (`--set-user`) |
| `Set-Curfew.cmd` | настроить ночной запрет (`--set-curfew`), правишь `START`/`END`/`ENABLED` |
| `Reset-Time.cmd` | мгновенный сброс времени в 0 (кладёт `reset.flag` в `%ProgramData%\TimeGuard`, служба его подхватывает) |
| `Check-Client.cmd` / `Diagnose.cmd` | диагностика без/с админом (см. §10) |

**Фундамент защиты**: учётка ребёнка — **стандартная (не администратор)**. Тогда службу SYSTEM
нельзя остановить/убить, а Диспетчер задач заблокирован политикой только для неё. Честная граница:
100%-й неубиваемости без драйвера/protected-process нет; для ребёнка/не-технаря достаточно.

**Родитель на нескольких ПК**: тот же `pairing.json` импортировать в SetupWindow. Коды временные,
синхронизация не нужна. `pairing.json` содержит секрет — хранить бережно, после установки удалить с флешки.

## 9. Решённые проблемы (не наступить снова)

Эти три бага стоили долгой отладки — держи в голове при доработках:

1. **Агент не стартовал (STATUS_DLL_INIT_FAILED 0xC0000142)**: `STARTUPINFO` маршалилась в ANSI,
   а вызывался `CreateProcessAsUserW`, из-за чего портилось имя рабочего стола `winsta0\default`.
   Фикс: `[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]` на STARTUPINFO.
2. **Управляемый код агента не запускался**: `CreateProcessAsUser` вызывался без командной строки
   (`lpCommandLine = null`) → нет argv[0] → .NET apphost не находит себя. Фикс: передавать
   `StringBuilder("\"<путь к exe>\"")`.
3. **Заглушка не получала статус (дедлок канала)**: обе стороны делали блокирующий `Flush`/`Write`
   на именованном канале до чтения друг друга. Фикс: писать в поток **без Flush** и задать каналу

## 14. Сеть: порты и протокол

Все сетевые функции — поверх LAN (кроме обновлений из GitHub Releases). Коды (§3) сети не требуют.

### 14.1 Порты

| Порт | Кто слушает | Назначение |
|---|---|---|
| TCP `38765` | служба на клиенте (`HistoryServer`) | `GET/POST /timeguard/history` (журнал, `?limit=1..500`), `POST /timeguard/control` (`status`/`add`/`reset`) |
| TCP `38766` | приложение родителя (`ParentOnlineServer`) | `POST /timeguard/request-time` — запрос времени от клиента |
| UDP `38767` | оба (клиент — `ParentDiscoveryListener`, родитель — `ParentOnlineServer`) | подписанные маяки обнаружения |

Константы: `HistoryProtocol.Port` (38765; родитель = `Port + 1`), `DiscoveryProtocol.Port`.
Клиент и родитель на одном ПК конфликтуют за UDP `38767`: второй процесс автообнаружение не получит.

### 14.2 Подпись запросов (`HistoryProtocol.cs`, `ReplayGuard.cs`, `LanHttpRequest.cs`)

Заголовки каждого запроса:

| Заголовок | Значение |
|---|---|
| `X-TimeGuard-Machine` | `machineId` пары (сравнивается точно) |
| `X-TimeGuard-Timestamp` | unix-время в секундах |
| `X-TimeGuard-Nonce` | hex, 1..64 символа (клиент генерирует 16 случайных байт) |
| `X-TimeGuard-Signature` | hex(HMAC-SHA256(секрет пары, подписываемая строка)), нижний регистр |

Подписываемая строка (UTF-8, разделитель — символ перевода строки `\n`):

```
machineId\ntimestamp\nnonce\nroute\nsha256hex(body)
```

- `route` — путь без query (`/timeguard/history`, `/timeguard/control`, `/timeguard/request-time`); query (`limit`) не подписывается.
- `sha256hex(body)` — SHA-256 тела в нижнем hex; для запроса без тела — хэш пустой строки. Тело уходит теми же байтами, что подписаны.
- Окно времени **±300 с** (`TimestampWindowSeconds`) относительно часов принимающей стороны.
- **Защита от повтора**: `ReplayGuard` запоминает пару `(timestamp, signature)` (подпись нормализуется в нижний регистр),
  повтор отклоняется, записи с timestamp старше окна удаляются. Отдельные экземпляры на обоих серверах
  (`HistoryServer`, `ParentOnlineServer`). Память процесса: после перезапуска службы/родителя повтор возможен до конца окна.
- Подпись сравнивается через `FixedTimeEquals`; ответы сервера **не подписаны**.

Лимиты разбора (`LanHttpRequest.ReadAsync`) и ответы:

| Условие | Код |
|---|---|
| тело (`Content-Length`) больше 32 КБ | `413` |
| строка заголовка больше 8 КБ или заголовков больше 32 | `431` |
| есть `Transfer-Encoding` (chunked не поддерживается) | `411` |
| неверная строка запроса, нечисловой `Content-Length`, обрыв тела | `400` |
| нет/неверные заголовки подписи, подпись вне окна, повтор | `401` |
| неподдерживаемый метод или маршрут | `405` (служба для неизвестного пути — `404`) |

### 14.3 Запрос дополнительного времени

1. Ребёнок нажимает на таймер в агенте, запрос уходит службе по именованному каналу (`IpcProtocol`).
2. Служба шлёт подписанный `POST /timeguard/request-time` на родителя (`http://<host>:38766`; адрес — введённый
   или найденный по маяку). Тело: `OnlineTimeRequest` (`machineId`, `minutes` 1..`MaxMinutes`, `reason`).
   Таймаут клиентского `HttpClient` — 6 минут.
3. Родитель проверяет подпись и повтор, показывает запрос в «Онлайн-управлении» и держит соединение до решения (до 5 минут;
   по истечении — ответ «Родитель не ответил вовремя»). Адрес клиента для следующего шага — адрес источника запроса.
4. При одобрении **родитель сам** отправляет подписанную `POST /timeguard/control` с `{"action":"add","minutes":N}`
   на клиента (`HistoryClient.ControlAsync`, таймаут 8 с). Служба клиента выполняет `GuardEngine.AddMinutes`.
5. Родитель отвечает клиенту `OnlineTimeResponse`; `Accepted=true`, только если команда `add` реально выполнена на клиенте.
6. **Служба минуты по ответу родителя не добавляет** — ответ не подписан, адрес родителя ребёнок может подменить.
   Поэтому ответ используется только для показа сообщения в агенте.

### 14.4 Обнаружение (`DiscoveryProtocol.cs`)

- Родитель каждые 5 с шлёт broadcast на `255.255.255.255:38767`, клиент отвечает одноадресно на адрес отправителя.
  Принимающая сторона ведёт непрерывное чтение сокета (отдельно от отправки).
- JSON (camelCase): `kind` (`TimeGuard.Parent`/`TimeGuard.Client`), `machineId`, `name`, `port`, `timestamp`, `signature`.
  Родитель указывает `port` 38766, клиент — 38765.
- Подпись: hex(HMAC-SHA256(секрет, `kind\nmachineId\nname\nport\ntimestamp`)); допуск по времени **±30 с**.
  Повтор маяка не отслеживается. Родитель принимает только ответы со своим `machineId`.
- Адреса запоминаются после обнаружения (`ClientHost` у родителя, адрес родителя в памяти службы).
- Тесты: `DiscoveryProtocolTests`, `HistoryProtocolTests`, `ReplayGuardTests`, `LanHttpRequestTests`.

### 14.5 Версия и проверка обновлений

- Единственный источник версии приложений — `Directory.Build.props` (`<Version>`). Те же числа должны быть в
  `installer/client.iss` (`AppVersion`), `installer/parent.iss` (`#define Version`) и в теге релиза `vX.Y.Z`;
  `release.yml` первым шагом проверяет совпадение и падает при расхождении (иначе установленная версия
  «отстаёт» от тега и приложение предлагало бы обновление бесконечно).
- Кнопки «Проверить обновление» (родитель — `MainWindow`, клиент — `ClientControlWindow`) сначала вызывают
  `UpdateChecker.CheckAsync`: он читает тег из редиректа `releases/latest` (без API и его лимитов) и сравнивает
  с версией сборки. Установщик скачивается и запускается **только если релиз новее**; иначе показывается
  «Установлена последняя версия». Раньше установщик скачивался и запускался всегда.
- Версия 1.2.4 — первая со встроенной версией и проверкой; копии старше неё получают обновление только вручную
  (запуск нового установщика).
